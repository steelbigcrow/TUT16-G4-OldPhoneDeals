# 并行执行排程（仅 Playwright MCP）

## 1. 适用范围与原则

- 本排程仅适用于 `通用E2E案例矩阵-Playwright-MCP.md` 的 48 条用例（`G/A/U/S/M/R`）。
- 执行工具仅允许 Playwright MCP（如 `browser_navigate`、`browser_snapshot`、`browser_network_requests`、`browser_console_messages`）。
- 并行目标：减少等待时间，同时避免共享测试数据互相污染。

## 2. 双人并行分工（2 人）

> 建议按“用户侧链路 vs 管理/卖家侧链路”拆分，冲突最小。

| 测试同学 | 负责模块 | 用例编号 |
| --- | --- | --- |
| Tester-A | 公共 + 认证 + 用户主链路 | `G-01~G-06`、`A-01~A-10`、`U-01~U-12` |
| Tester-B | 卖家 + 管理员 + 异常恢复 | `S-01~S-05`、`M-01~M-10`、`R-01~R-05` |

执行节奏建议：
- 第 1 轮：两人各自先跑本分工内 `P0`。
- 第 2 轮：跑 `P1`。
- 第 3 轮：补 `P2` 与失败重跑。

## 3. 三人并行分工（3 人）

> 建议按“前台用户域 / 卖家域 / 管理域”三段切分。

| 测试同学 | 负责模块 | 用例编号 |
| --- | --- | --- |
| Tester-A | 公共与认证 | `G-01~G-06`、`A-01~A-10` |
| Tester-B | 用户交易链路 | `U-01~U-12`、`R-01~R-02` |
| Tester-C | 卖家与后台治理 | `S-01~S-05`、`M-01~M-10`、`R-03~R-05` |

执行节奏建议：
- 第 1 轮（三人同时）：各自 `P0`。
- 第 2 轮（三人同时）：各自 `P1`。
- 第 3 轮：集中处理失败用例与阻断缺陷复测。

## 4. 共享数据冲突规避规则

### 4.1 重置时机（`/api/e2e/reset`）

- 只允许“当轮值班人”触发重置，避免多人同时 reset。
- 固定时机：
  - 每轮并行开始前 1 次（P0 前、P1 前、P2/重跑前）。
  - 不在别人执行中途 reset。
- 若某人必须中途 reset，先在群内报备并等待“其他人完成当前用例”。

### 4.2 账号隔离

- 每人使用独立账号池，不混用：
  - Tester-A：`pw_ta_buyer_*` / `pw_ta_seller_*` / `pw_ta_admin_*`
  - Tester-B：`pw_tb_buyer_*` / `pw_tb_seller_*` / `pw_tb_admin_*`
  - Tester-C：`pw_tc_buyer_*` / `pw_tc_seller_*` / `pw_tc_admin_*`
- 冻结、删号、改密类用例只操作“本人前缀账号”。
- 禁止用例间共享登录态；每条用例开头显式登录或显式清 token。

### 4.3 商品 ID 隔离

- 每人固定商品 ID 段，禁止跨段改删：
  - Tester-A：`phoneId 1000~1999`
  - Tester-B：`phoneId 2000~2999`
  - Tester-C：`phoneId 3000~3999`
- 涉及删除/上下架/编辑的用例，只操作本人 ID 段内商品。
- 若用例依赖“系统预置商品”，只读不改；要改则先复制出本人专属商品再操作。

## 6. 合并规则（负责人）

- 按用例 ID 去重：同一用例多份结果时，优先保留“最新一次且证据完整”的记录。
- 缺陷去重：相同接口 + 相同现象合并为同一缺陷，保留多环境/多账号复现证据。
- 发布口径先看 `P0`：任何 `P0` 未通过即整体结论为“不可发布”。
